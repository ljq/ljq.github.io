【SOP实操】一台高配服务器，用 k3s + Gitea 从零搭建 Golang 应用的轻量级生产发布环境

一、对于云部署解决方案，为什么选 k3s，而不是标准 k8s

虽然AI时代，但作为软件工程的重要技术工程部分，还是要深入掌握云的使用。

在“一台高配服务器”这个约束下，标准 Kubernetes 的控制面本身就是一种负担。kubeadm 部署的 k8s 控制面包含 API Server、Scheduler、Controller Manager、etcd 等独立组件，仅控制面就需要至少 2 vCPU + 2 GB RAM，且各组件独立部署、独立排障。k3s 则把这些打包成一个不到 70 MB 的单一二进制，默认使用 SQLite 作为单节点数据存储，并内置 containerd、Flannel、Traefik Ingress 和 Klipper LB。关键事实：k3s 是 CNCF 认证的 Kubernetes 发行版，不是 fork，也不是“简化版 API”——任何合法的 Kubernetes manifest 在 k3s 上同样生效。

维度标准 k8s（kubeadm）k3s（单节点模式）
控制面形态多组件独立部署单一二进制
默认数据存储etcd（必须）SQLite（单节点）；etcd 可选
控制面最低资源2 vCPU + 2 GB RAM（不含 etcd 和工作负载）官方资源剖析：Server 带工作负载约 6% CPU + 1.6 GB RAM（x86）
内置组件需自行安装 CNI、Ingress、LB内置 Flannel、Traefik、Klipper LB、containerd
API 兼容性标准 Kubernetes API100% 兼容
适用场景多节点、大规模、企业级高可用边缘、单机/小集群、轻量生产

需要特别说明一个常见的误读：k3s 官方“最低 512 MB”指的是 agent 节点的最低门槛，且只是“能启动”级别。真实生产工作负载下，官方资源剖析显示 Server 带工作负载的基线约为 1.6 GB RAM（SQLite/Kine）或 1.6 GB RAM（嵌入式 etcd），CPU 占用约 6%（以 Intel 8375C 为基准）。因此，“一台高配服务器”的正确配置区间是 4–8 vCPU、8–16 GB RAM、NVMe SSD，而不是贴着最低线走。

单节点的根本限制在于控制面单点：Server 一旦重启或宕机，Agent、Ingress、API 全部失联，业务随之中断。本文的方案定位是“轻量级生产环境”——用单节点承载中小流量业务，通过流程规范、备份和资源隔离来管理风险，而不是追求控制面高可用。当业务增长到无法容忍控制面中断时，再按 k3s 的演进路径将 SQLite 平滑迁移到三节点嵌入式 etcd。

二、硬件配置建议与技术栈总览

硬件配置

单台高配服务器建议配置：

资源建议值说明
CPU4–8 vCPUk3s 控制面开销低，主要留给 Gitea、Runner 构建和应用负载
内存8–16 GBGitea 小团队约 2–4 GB；Runner 构建峰值额外 2–4 GB；k3s 控制面约 1.6 GB；剩余给应用
磁盘200 GB+ NVMe SSD镜像层、Gitea 仓库、SQLite 数据库、构建缓存都需要低延迟存储
操作系统Ubuntu 22.04 / 24.04 LTS社区验证充分，k3s 兼容性好

如果同时运行 Gitea、act_runner 和一个简单的 Golang Web 应用，4 vCPU / 8 GB RAM 是舒适起点；如果 Runner 构建频繁，8 vCPU / 16 GB 留出足够余量。

架构与数据流

这个方案将 Gitea Registry、act_runner、k3s 压缩在同一台机器上，镜像拉取不出节点，构建和部署链路极短。核心决策是 用 Gitea 自带的 Container Registry 作为唯一镜像仓库，避免引入外部 registry 带来的认证和网络复杂度。

九、生产注意事项与最佳实践

9.1 单节点的风险必须被明确管理

单节点 k3s 的控制面是单点。一旦 Server 进程崩溃或节点重启，API、Ingress、已调度 Pod 的健康检查都可能受影响。可以做的缓解措施：

  • 备份 SQLite 数据：k3s 单节点默认数据存储在 /var/lib/rancher/k3s/server/db/，但 k3s 官方明确说明不支持对 SQLite 做在线快照，建议直接复制 /var/lib/rancher/k3s/server 目录来备份。将备份任务做成 cron，复制到另一块磁盘或远端对象存储。
  • 为未来迁移 etcd 留好路径：不要在早期把 Server 地址硬编码到各处。Agent 注册地址如果写死单机 IP，后续迁移到多 Server 时需要逐台修改。尽量在证书中加入 SAN 或使用可切换的 DNS 名称。
  • 接受“计划内维护窗口”：单节点方案不适合零停机要求极高的业务。把 k3s 升级、内核补丁安排在低峰窗口，并提前验证备份可恢复。

9.2 资源限制不是可选项

轻量不等于不需要观测。每个 Deployment 都应设置 requests 和 limits，防止构建任务或应用内存泄漏拖垮 k3s 和 Gitea。至少部署一个轻量监控（node-exporter + 简单告警，或 netdata），在内存打满之前收到通知。

9.3 Runner 权限最小化

本文为了快速跑通给 act-runner 绑定了 cluster-admin。生产环境中应收窄为仅对目标 namespace 的 Deployment、Service、Pod 的 get/list/watch/patch/update 权限。Runner 是 CI 执行环境，一旦仓库的 Actions 被恶意修改，过大的权限就是安全缺口。

9.4 镜像 tag 策略

工作流同时推送了 SHORT_SHA 和 latest，但 kubectl set image 使用的是 SHORT_SHA。不要在生产部署中使用 latest 作为实际拉取 tag，因为 containerd 的 imagePullPolicy: IfNotPresent 可能导致节点不拉取新镜像。每次 commit 使用唯一 tag 是滚动更新可靠生效的前提。

9.5 Gitea Registry 的 TLS

本文使用 HTTP NodePort 作为 Registry 端点，适用于单机内网或实验环境。生产环境应配置 TLS：可以在 Traefik 或 ingress-nginx 上为 gitea.<domain> 配置证书，然后将 registries.yaml 中的 endpoint 改为 https://，并去掉 insecure_skip_verify: true。Gitea 官方镜像支持通过反向代理终止 TLS，后端 HTTP 保持不变。

9.6 不要在 Server 节点上运行不受控的构建负载

act_runner 的构建任务可能产生 CPU 和内存尖峰。单节点场景下 Runner 和应用共享同一台机器，必须给 Runner 设置比应用更宽松但仍有上限的 resources.limits，避免 docker build 吃满内存导致 k3s 的 kubelet 被 OOM killer 终止。如果构建频率升高，最有效的优化不是升级服务器，而是把 Runner 拆到独立节点，或者使用 Kaniko 并限制其并发度。

十、验证清单（SOP 收尾）

按以下顺序逐项确认，即可判定环境“可发布”：

  1. kubectl get nodes → Ready。
  2. Gitea Pod Running，浏览器可登录，Registry 已启用。
  3. act-runner 在 Gitea Runner 页面显示在线。
  4. registries.yaml 已写入并重启 k3s，containerd 配置中包含 Gitea Registry 端点。
  5. 在仓库中推送一次代码，Actions 运行成功，镜像出现在 Gitea 的 Packages 页面。
  6. kubectl get pods -l app=go-web-demo 显示新 ReplicaSet 的 Pod 为 Running，kubectl rollout history 可追溯。
  7. 通过 NodePort 访问应用，/healthz 返回 ok。
  8. SQLite 备份 cron 已配置，并手动执行一次恢复演练（在非生产副本上） 。

这套方案的价值不在于它“用了 k3s 和 Gitea”，而在于它把 代码推送 → 镜像构建 → 镜像推送 → Kubernetes 滚动更新 压缩到一台机器上的单条流水线中，每一步都有明确的配置文件和验证方法。它适合中小团队在没有专职平台工程师的情况下，用最低的运维表面积获得可重复、可追溯的发布能力。当单节点的控制面单点成为真实痛点时，再按 k3s 的演进路径扩展为三节点 etcd 高可用——那时开发者已经有了稳定的 CI/CD 流程和镜像仓库，迁移的代价是可控的。
