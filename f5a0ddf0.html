痛点：如果直接把短文本喂给模型，大量的 <pad> 会浪费算力。
方案：将多条文本拼接，用 <eos> 隔开，并重新生成 Labels，确保模型只在真实 token 上计算 Loss。

五、 完整实施 Checklist (避坑指南)

在真正跑通这套流程时，请务必对照以下 Checklist：

📊 数据阶段

  • 去重检查：是否使用了 MinHash 或 SimHash 去除重复文档？（重复数据会导致模型在特定 token 上 Loss 异常低，引发梯度爆炸）。
  • Packing 检查：打包后的 labels 是否正确右移？跨文本拼接处是否用 <eos> 隔离？（防止模型把两篇不相关的文章当成连贯上下文）。

🏗️ 预训练阶段

  • MoE 负载均衡：在 TensorBoard 中监控 aux_loss。如果 aux_loss 持续为 0 或极大，说明 Router 坍塌（所有 token 都去了同一个 Expert）或梯度消失。
  • EP 通信检查：如果使用了 Expert Parallelism (EP)，检查 GPU 间的 All-to-All 通信时间占比。如果占比 > 20%，说明网络带宽是瓶颈，需调整 EP 和 TP 的比例。

🎯 对齐阶段 (SFT/DPO)

  • Loss Masking：SFT 时，是否只对 output 计算 Loss？（如果对 instruction 也计算 Loss，模型会学到“如何提问”而不是“如何回答”）。
  • DPO 数据质量：DPO 对数据质量极度敏感。chosen 和 rejected 的差异必须明显，且 rejected 不能是毫无逻辑的乱码（会导致模型学坏）。

🚀 部署阶段

  • 量化掉点评估：INT4 量化后，务必在 MMLU、GSM8K 等榜单上跑一下评测。如果复杂推理任务掉点超过 5%，建议退回 INT8 或 FP16。
  • KV Cache 显存监控：在 vLLM 中，监控 gpu_cache_usage_perc。如果经常达到 100%，说明并发请求过多，需要增加 max-model-len 限制或增加 GPU 节点。

延伸阅读

  • PyTorch：Transformer 模块官方文档，理解基础 Transformer 组件与接口。

  • Hugging Face Transformers：量化官方文档，了解 INT8、4-bit 与 QLoRA 的工程实现。

模型技术和算法革新经常在变，以 Tiny9 的模型名称与参数配置用于教学示例，文中的代码是逐步构建研发系统的基础实现，并非已完成训练、全面验证和性能优化的商业级模型发布包。
