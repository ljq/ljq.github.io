DevOps开发者必备技能之：面向8人以下小型团队的 Gitea DevOps 最小化实践指南

在小型团队（一般8人以下）中，引入庞大的 DevOps 工具链（如 GitLab + Jenkins + Kubernetes）往往会导致“工具维护成本高于业务开发成本”。对于小团队而言，轻量、够用、易维护才是核心诉求。

以下将基于 Debian 13 操作系统，以 Gitea 最新稳定版 为核心，为你梳理一套完整的 DevOps 最小化 SOP（标准作业程序）。我们将从选型、安装、分支规范，一直走到 PHP 和 Golang 项目的自动化 SSH 部署，全程不依赖 Docker，回归最纯粹的 Git + SSH 部署模式。

一、 为什么选择 Gitea？（选型分析）

对于8人以下的小型团队，Gitea 是当之无愧的“性价比之王”：

  1. 极致轻量：单个二进制文件，内存占用极低，在 1核2G 的廉价 VPS 上即可流畅运行。
  2. 功能够用：支持 Issues、Milestones、Wiki、PR 审查，满足日常研发管理。
  3. 原生 CI/CD：内置 Gitea Actions（兼容 GitHub Actions 语法），无需额外搭建 Jenkins，直接在代码仓库内完成流水线配置。
  4. 部署极简：无需复杂的容器编排，直接 SSH 部署到目标服务器，对小团队的前后端项目极其友好。

三、 小型团队 DevOps 最小化 SOP 与分支规范

对于小团队，我们采用简化版 GitFlow，严格映射三套环境。

1. 分支与环境映射

分支名称对应环境触发部署说明
dev开发环境 (Dev)合并入 dev 时开发人员日常联调、功能开发。
test测试环境 (Test)合并入 test 时QA 介入测试，验收功能。
prod生产环境 (Prod)合并入 prod 时正式发布，面向最终用户。

2. 提交规范 (Conventional Commits)

强制要求 Commit Message 遵循规范，便于后续生成 Changelog：

  • feat: 新增用户登录功能
  • fix: 修复订单金额计算错误
  • docs: 更新 API 文档

3. 分支保护与 PR 流程 (SOP)

在 Gitea 仓库设置中，为 dev、test、prod 开启分支保护：

  1. 禁止直接 Push：所有分支必须通过 Pull Request (PR) 合并。
  2. 合并策略：推荐使用 Squash and merge（压缩合并），保持主干提交历史整洁。
  3. 流转 SOP：
    • 开发从 dev 切出 feature/xxx 分支，开发完成后 PR 到 dev。
    • dev 验证通过后，由 Tech Lead 发起 PR 将 dev 合并到 test。
    • test 验收通过后，发起 PR 将 test 合并到 prod，触发生产部署。

四、 配置 Gitea Actions Runner 与 SSH 免密

为了实现“无需 Docker，直接 SSH 部署”，我们需要在 Gitea 服务器上安装 Runner，并配置到目标服务器的 SSH 免密登录。

1. 安装 act_runner

配置 Runner 使用 host 模式（不依赖 Docker），编辑 ~/.act_runner/config.yaml，将 container 相关配置注释或禁用，确保命令直接在宿主机执行。

2. 配置 SSH 密钥与 Secrets

在 Gitea 服务器上生成 SSH 密钥，并将公钥添加到目标部署服务器的 ~/.ssh/authorized_keys 中。

在 Gitea 仓库的 Settings -> Secrets and variables -> Actions 中，添加以下 Secrets：

  • SERVER_IP: 目标服务器 IP
  • SERVER_USER: 目标服务器用户名 (如 deploy)
  • SSH_PRIVATE_KEY: 刚才生成的私钥内容 (cat /home/git/.ssh/id_ed25519)

七、关于项目环境变量的配置和管理

在上一篇文章中，我们完成了 Gitea 的基础搭建与最基础的 SSH 部署流水线。但在实际研发中，“代码与配置分离” 是 DevOps 的铁律。

对于 8 人以下的小型团队，最容易踩的坑就是：为了图方便，把数据库密码、第三方 API Key 直接硬编码在代码里，或者在每次部署到 dev/test/prod 时，手动去服务器上修改配置文件。这不仅带来了极大的安全隐患，也导致了部署效率低下和人为错误。

本文将作为进阶补充，深入探讨在 Gitea 体系下，如何优雅、安全地管理多环境的部署配置与变量。

1. Gitea 的解决方案：Secrets 与 Variables 体系

Gitea（特别是 1.20 版本之后）引入了非常完善的 Environments（环境） 概念，配合 Secrets（机密） 和 Variables（变量），完美契合了小型团队对 dev/test/prod 三套环境的隔离需求。

1.1. 核心概念区分

类型适用场景在 Workflow 中的表现示例
Secrets (机密)敏感信息，绝对不可明文出现在代码或日志中。${{ secrets.MY_SECRET }} (Gitea 会自动在日志中打码 ***)DB 密码、OSS 密钥、SSH 私钥、微信支付 Key
Variables (变量)非敏感的配置项，不同环境值不同，明文可见。${{ vars.MY_VAR }}API 基础域名、前端 CDN 地址、环境标识符

1.2 利用 Environments (环境) 实现精细化隔离

在 Gitea 仓库的 Settings -> Environments 中，你可以创建 dev、test、prod 三个环境。
核心优势：你可以为每个环境配置独立的 Secrets 和 Variables。

  • Dev 环境：配置测试库密码、测试域名。
  • Prod 环境：配置生产库密码、正式域名。甚至可以配置部署保护规则（例如：部署到 prod 必须经过 Tech Lead 审批）。
