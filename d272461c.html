纯Bash实现终端进度条task任务处理的常用方式（无外部依赖）

在编写Bash脚本时，我们经常会遇到耗时较长的任务（如批量下载、大文件处理、数据库迁移等）。如果终端只是静静地“假死”，用户往往会感到焦虑，甚至误以为脚本卡死而强制中断，这时候引入必要的loading跟踪进度能最大限度帮助开发者了解任务的执行情况。

一个优雅的进度条不仅能缓解用户的等待焦虑，还能提升脚本的专业感。虽然市面上有 pv、dialog 等强大的外部工具，但在很多受限环境（如精简版Docker镜像、嵌入式设备、跨平台CI/CD）中，不依赖任何外部扩展库，纯靠Bash原生特性实现进度条，对开发者来说都是一项非常实用且简单的技能，所谓大道至简，善用任务处理机制和状态跟踪，事半功倍。

通过逐步实现从最简单的“旋转菊花”到复杂的“多任务并行进度条”，既帮助理解也可以日常工作中使用。

一、 核心原理：终端控制字符

在开始写代码前，我们需要了解Bash控制终端输出的两个核心“魔法”：

  1. 回车符 \r：将光标移动到当前行的行首，但不换行。配合 printf 或 echo -n，可以实现原地覆盖更新文本。
  2. ANSI 转义序列：如 \e[nA（光标上移n行）、\e[0G（光标移动到行首）。用于实现多行内容的动态刷新。

二、 基础篇：最简单的“旋转菊花” (Spinner)

当你不知道任务具体需要多久，只知道它还在运行时，一个简单的加载动画是最好的选择。

实现思路

利用一个字符数组（如 - \ | /），在后台任务运行时，循环打印并覆盖当前行首字符。

三、 进阶篇：基于百分比的线性进度条

当我们知道任务的总步数（如下载100个文件，处理1000行数据）时，百分比进度条能提供更精确的预期。

实现思路

  1. 计算当前百分比：percent = current * 100 / total。
  2. 计算进度条填充长度：利用Bash的字符串重复特性或 printf 的宽度控制。
  3. 使用 \r 原地刷新。

四、 高级篇：带时间估算 (ETA) 的动态进度条

在复杂的脚本中，我们希望能看到“预计剩余时间”。

实现思路

记录任务开始时间，通过已用时间和当前进度，推算出总时间和剩余时间。为了保持代码纯粹，我们使用 date +%s 获取时间戳，并用 awk 进行简单的浮点运算（awk 是POSIX标准工具，不算外部扩展库）。

注意事项

虽然所有主流发行版本都自带相关 COMMAND 命令，但像 AWK 可能需要现安装才可以，这点注意即可，避免环境兼容性问题，做好检查⚠️。

五、 终极篇：并行任务的进度条

这是相对最复杂的场景。假设我们要同时下载10个文件，每个文件有自己的进度。（但也要注意任务的拆分和终端文本本身的承载能力）

痛点：子进程在后台运行，无法直接控制父进程的终端输出，如果多个子进程同时 printf，终端会乱成一锅粥。

实现思路（进程间通信 + 光标控制）

  1. 状态分离：子进程不直接输出UI，而是将自己的当前进度写入独立的临时文件（如 progress_1.tmp）。
  2. 主进程聚合：父进程开启一个 while 循环，每隔0.2秒读取所有临时文件，计算总进度和各个子任务进度。
  3. 多行刷新：利用ANSI转义码 \e[nA（光标上移n行），实现多行UI的整体刷新。

六、 总结与最佳实践

  1. 兼容性第一：尽量使用 printf 代替 echo -ne，因为不同系统（如 macOS 的 BSD echo 和 Linux 的 GNU echo）对 -e 的解析存在差异。
  2. 优雅降级：如果脚本可能在非交互式环境（如 cron job 或 CI 管道）中运行，建议检测 tty，如果不是终端则禁用进度条，直接输出纯文本日志：
  3. 性能考量：在并行进度条的主循环中，sleep 0.2 是必要的。如果轮询太频繁（如 sleep 0.01），会大量消耗CPU去读取文件和刷新终端，反而拖慢实际任务的执行。
  4. 临时文件清理：使用 trap 'rm -f progress_*.tmp; tput cnorm' EXIT 可以在脚本被 Ctrl+C 中断时，确保临时文件被清理且光标恢复正常。
